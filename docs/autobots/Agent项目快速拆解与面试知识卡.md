# Autobots / agplateform 项目面试速记

> 目标：先讲清项目，再讲清 Agent，最后讲清你做了什么。
>
> 阅读顺序：项目定位 -> 架构 -> 两条流程 -> 个人职责 -> 面试回答。

## 一、先分清两个项目

这是最重要的一步。

| 项目 | 一句话定位 | 核心能力 |
| --- | --- | --- |
| Autobots | 面向企业客户的 AI 智能客服应用 | 知识库、RAG 问答、会话、线索、渠道、运营 |
| agplateform | 支撑不同 Agent 应用的通用平台 | Agent 配置、模型、工具、Runtime、租户、配额、编排 |

它们的关系可以类比为：

```text
agplateform = Agent 基础设施和平台能力
Autobots    = 使用平台能力实现的客服业务产品
```

面试时不要把 Autobots 的所有问答都说成“自主 Agent”。

- Autobots 主问答更接近：`知识检索 -> 大模型生成 -> 流式返回`。
- agplateform Runtime 更接近：`模型判断 -> 调工具 -> 获取结果 -> 继续判断`。

### 各层负责什么

| 层 | 职责 |
| --- | --- |
| 前端 | 配置 Agent、管理知识、发起对话、展示流式结果和工具状态 |
| Gateway | 认证、路由、注入可信的用户和租户信息 |
| Java 业务层 | 用户、知识编排、线索、报表和外部服务适配 |
| Python AI 层 | 文档处理、检索、Prompt 组装、模型调用和会话 |
| agplateform | 提供通用 Agent、模型、工具、权限和运行时能力 |
| WebGPT | 执行网页抓取，不负责用户权限和在线问答 |

为什么使用多种语言：不是为了显得复杂，而是利用各自生态。

- Java 处理稳定的企业业务和事务。
- Python 集成模型、RAG 和 AI SDK。
- Rust 承接高性能 Agent Runtime。
- Go 处理多 Agent 通信和编排。

## 三、业务主线：企业知识如何变成客服回答

只需要记住下面这一条端到端流程。

```text
1. 用户在管理端上传文件或输入网页 URL
2. 后端创建知识处理任务，返回 task_id
3. 爬虫或文档服务获取并解析内容
4. 内容被切成多个 chunk
5. chunk 生成向量并写入 Milvus
6. chunk metadata 保存 task_id、来源、版本等信息
7. 用户向客服 Agent 提问
8. 服务端计算该用户/Agent 可以访问的 task_ids
9. 在 Milvus 中只检索这些知识
10. 检索结果与 Prompt 一起交给大模型
11. 答案通过流式响应返回前端
12. 系统保存会话，并执行线索抽取、用量统计等后置任务
```

### 这条流程里的四个关键点

**1. 为什么异步处理知识？**

爬取、解析和向量化耗时不可控。接口只负责接收任务，前端通过状态展示后续进度，避免请求超时。

**2. `task_id` 有什么用？**

它关联一次知识任务、数据库记录和向量 metadata。它是关联键，不是权限凭证。

**3. 如何防止检索到其他客户的知识？**

服务端根据用户、租户、Agent 和知识绑定关系计算允许访问的 `task_ids`，再作为向量检索过滤条件。不能相信前端传入的知识范围。

**4. 为什么提交成功不等于知识可用？**

```text
任务已接收 -> 内容已获取 -> 解析完成 -> 向量写入完成 -> 可以检索
```

只有最后一步完成，知识才真正生效。

## 四、Agent 主线：模型如何调用工具完成任务

普通聊天只生成文字；Agent 还能够执行动作。

```text
用户提出目标
    |
    v
Runtime 将 Prompt、历史、Tools 发送给模型
    |
    v
模型是否要求调用工具？
    |
    +-- 否 --> 输出最终答案
    |
    +-- 是 --> Runtime 校验工具和参数
                  |
                  v
              执行 Tool / MCP
                  |
                  v
              得到 tool_result
                  |
                  v
              回传给模型继续判断
```

可以把它概括为：

```text
Agent = LLM + Tool + Memory + Loop
RAG   = Agent 可以使用的一种知识能力
MCP   = Agent 接入外部工具和资源的标准协议
```

### Runtime 必须控制什么

- 最大循环次数，避免模型无限调用工具。
- 工具白名单和参数校验，避免越权操作。
- 超时、取消和费用预算。
- 工具执行沙箱及敏感数据脱敏。
- `tool_call_id`，用于关联调用和返回结果。
- 完整审计日志，记录谁在什么时间调用了什么工具。

## 五、你的前端工作在 Agent 系统中的价值

你不是只“画管理页面”。前端负责把不可预测的 Agent 执行过程变成用户能理解、能控制的产品。

| 前端工作 | 对应的 Agent 能力 |
| --- | --- |
| Agent 配置表单 | 模型、Prompt、知识和渠道的控制面 |
| 流式聊天 | 消费模型 token 和 Agent 执行事件 |
| 工具调用卡片 | 展示 tool call、执行中、成功和失败 |
| 停止回答 | 客户端取消，并推动服务端取消模型与工具任务 |
| 知识状态页面 | 展示异步任务状态和最终一致性 |
| Page Agent | 将 DOM 和浏览器操作变成 Agent 工具 |
| 语音交互 | ASR、VAD、TTS、打断和实时状态管理 |

### 流式前端必须懂的三个点

1. POST 流式请求通常使用 `fetch + ReadableStream`，而不是只支持 GET 的 `EventSource`。
2. 一次 `reader.read()` 不等于一条完整消息，需要用 `TextDecoder + buffer` 处理半包和粘包。
3. 停止更新 UI 不等于停止后端任务，需要 `AbortController` 和服务端断开检测配合。

## 七、准备三个项目故事

### 1. 前端生产构建优化：主讲个人工程能力

```text
问题：每次业务发版都重复构建 Arco 组件库
方案：组件库预构建 + 源码 SHA-256 + manifest 一致性校验
价值：减少重复构建，同时避免复用过期产物
```

没有可靠数据时不要编造提速比例，可以说后续会统计构建 P50/P95 和缓存命中率。

### 2. 知识异步摄入：主讲跨栈理解

```text
问题：爬取、解析、Embedding 无法在同步请求内稳定完成
方案：task_id + 状态机 + 后台处理 + 最终生效状态
风险：重复回调、任务丢失、数据库和向量库不一致
演进：持久化任务、Outbox、幂等消费、重试和补偿扫描
```

### 3. Agent 流式交互：主讲前端优势

```text
问题：token 和工具事件持续到达，用户还可能取消
方案：结构化事件、call_id、增量解析、批量渲染、工具状态卡
协同：服务端事件队列、心跳、断开检测和任务取消
```

## 八、最容易被追问的五个问题

**Autobots 是 Agent 还是 RAG 应用？**

主问答更接近可配置 RAG 应用；agplateform Runtime 中的动态工具选择和多轮执行更符合典型 Agent。RAG 可以是 Agent 的一项能力。

**为什么 Java 和 Python 同时存在？**

按业务稳定性和技术生态拆分。Java 负责企业业务，Python 负责快速变化的 AI 能力。代价是跨服务契约、错误处理和链路追踪更复杂。

**如何保证知识隔离？**

网关先认证，业务服务再授权；服务端计算可访问知识范围，并将它作为向量 metadata 过滤条件。

**为什么使用 SSE/HTTP 流而不是 WebSocket？**

文本生成主要是服务端向客户端单向推送，HTTP 流更简单。实时双向语音或高频控制场景再使用 WebSocket。

**AI 生成的后端代码算你的经验吗？**

算 AI 辅助交付经验，但不包装成长期纯手写后端经验。重点说明自己如何拆需求、限制生成方案、审查代码、补测试、联调和排障。

## 九、面试表达边界

面试前给经历贴标签：

- `[主导]`：你负责方案和主要实现。
- `[参与]`：你负责其中明确的一部分。
- `[AI 辅助]`：AI 生成代码，你负责判断、审查和验证。
- `[掌握]`：不是你实现，但你读过源码并能解释。
- `[建议]`：项目暂未实现，是你的演进方案。

不要说：

- “使用微服务所以性能高。”
- “使用向量库就不会产生幻觉。”
- “`task_id` 就是权限控制。”
- “代码里存在某个类，所以生产链路一定启用了它。”
- 没有统计依据的 QPS、准确率、业务收益或提速比例。
